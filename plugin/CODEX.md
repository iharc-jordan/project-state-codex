# Project State in Codex

Read this once when a Project State skill first runs in a task. The skill and bundled capability files describe their own domain behavior; this file only resolves Codex host differences.

- Current user direction and applicable `AGENTS.md` / `REQUIREMENTS.md` govern the task. A direct request authorizes its ordinary local work. Ask only for missing facts that materially affect correctness, scope, or authorization. Keep existing domain approval gates and obtain explicit authorization for external sends or publication unless already provided.
- Resolve `packs/`, `templates/`, `capabilities/`, and scripts from the installed `plugin/` payload, not from the operator's project. Use the current shell and actual available Codex tools. Do not infer that a connector, application, or paid entitlement is active from its bundled instructions.
- On Windows, invoke bundled Python helpers with `python -X utf8` using the available Python executable so Unicode status output works without global encoding changes.
- Locate the project through `project_list` when Project State MCP tools are available. If it serves the selected project, use its checked tools, preferring domain actions over general entity operations. Preserve `base_sha256` when updating existing entities. A server refusal is a refusal; never write around it through files. Use the file binding only for a local project that is not served. Cloud/deposit operation requires its configured connector and credentials.
- Codex starts plugin MCP servers in the installed directory. The existing `PROJECT_STATE_DIR` may bind a selected local facility before startup; without it the server may list no local project. Treat that as unserved, not a failed write or permission to bypass a refusal.
- For a general durable change, update the canonical entity, required state projections, and one attributed activity event through `project-state`. General entity and log calls are separate operations, not a transaction; inspect and report partial failures. Preserve unknown fields, existing records and legacy event aliases. Use `skills/project-state/scripts/event_identity.py` for repeat detection when no domain tool already handles it. Never append or regenerate the same event/result twice.
- Start routine reads with bounded summaries and open detail only as needed. Routine code work does not itself create a Project State facility or entity. Record material shared outcomes or a directly requested fact in the canonical owner. Reports are derived from canonical data; route each output to one owner.
- Install makes skills and capabilities available; enablement is per project. Do not create project caches, recurring schedules, external messages or publication as an installation effect. `automation/tasks.yaml` is the cadence registry. Recognize legacy Tender data as the same canonical Tender capability and retain it when enabling or disabling.
- Render answers in ordinary Codex conversation or supported panels. Preview a local HTML snapshot through a task-owned loopback server and Codex browser when requested. Use native Codex automation and native subagents only when the task calls for them; honor current model settings and available concurrency.
- Validate the changed behavior and stop when sufficient. Do not copy inaccessible private Claude documents or assume Claude/Cowork interfaces exist.
